# Issue 报告

这是给 AI Agent 看的 Issue 报告规范；人类提交者（可以参考规范但）请直接在 GitHub 上填写模板。

## 先确认授权

**真正实施报告前，请务必三思：你是否被用户授权提交**？如果没有，向用户提问；如果连用户都没有，就别提交。开 Issue、评论、发邮件、调用 tracker API 都算提交，没有明确授权就只交付草稿。

“帮我看看”“整理一下”不等于授权提交；用户明确说“提交/发到 Issues”才算。

## 核心判断

Issue 的长度取决于**维护者还需要知道什么**，不是报告者做了多少调查。目标是让维护者快速识别、判断、复现、修复，而不是展示完整的故障调查过程。

- 正文只保留理解、判断、复现和修复问题所必需的信息。
- 补充证据只有在能够核验结论、判断复现概率或验证修复效果时才作为附件提供。
- 不影响上述判断、也没有独立核验价值的信息直接删除。
- 也不要为了短小而机械删除：某段源码分析如果正是维护者理解问题的关键，就留下。
- 不要求定位到具体代码或根因；已定位到位置可以写，但不作为提交前提。
- 不要把 Issue 写成故障调查报告：调查过程本身有价值，但做了多少调查不是正文内容，维护者也无意了解。

## 标题

标题只承担识别功能：平台/环境（必要的时候）、关键症状、发生条件（如偶发）。默认不写内部实现机制（函数名、模块名、竞态等）；只有组件或公开 API 名称本身是识别故障最有效的信息时才保留。不写未验证的根因假设。

- 不把次要现象特征（用时 `N/A`、峰值 `0 B` 之类）堆进标题，留最能区分问题的一个症状。
- 不用“监控不完善”这类宽泛评价替代症状。

例：

- 差：`[Bug] Windows 下时限内正常退出的子进程被误判为 MLE（用时 N/A、峰值 0 B）：ProcessSupervisor 监控分支与 child.wait() 的 select 竞态`
- 好：`[Bug] Windows 下正常退出的子进程偶发被误判为 MLE`

## 按项目模板写

先读项目的 Issue 模板（本仓库在 `.github/ISSUE_TEMPLATE/`：Bug 用 `BugReport.yml`，功能请求用 `FeatureRequest.yml`），按字段填写；模板的节不自行增删或改名。

本仓库 Bug 模板的关键字段：

- 期望的行为 / 实际结果：对应“现象与期望”。
- 重现步骤：最小可复现步骤。
- 截图/录屏：可选。
- 诊断信息：运行 `tuack-ng develop diagnostic`，按模板要求提供。若要求粘贴原始输出，不得删减、改写或重新排版；不要在其他字段重复其中已有的环境信息；与问题无关的敏感信息按项目要求处理，不要机械公开。

模板要求必填的内容即使觉得不必要也要保留；模板之外的补充信息放对应字段或附件，不另起一套结构。

## 尊重内容归属

开发者维护的备注、章节与模板结构不属于报告者可自行修改的内容；未经明确授权，不得擅自删除、移动或改写。整理报告时只修改授权范围内的内容，不能因为“按模板填写”就删掉开发者新增的章节。

## 区分事实与推断

- 观测到的异常；
- 从源码或代码路径推导出的可能机制；
- 已被实验验证的因果关系。

三者不要混写。推断用“可能/疑似”并给出依据，不把未验证假设写成结论。源码里存在可疑路径，不等于本次故障就是它。

## 证据取舍

- 不要求根因分析：根因已明确且能直接帮助理解或修复时可以保留；只是推测时，不要为了填充报告而强行分析。
- 不复述实验过程，只留复现所需的最少步骤。
